# Breaking Changes Management | n8n-io/n8n | DeepWiki

This document describes how n8n manages, documents, and communicates breaking changes to ensure users can smoothly upgrade their installations. It covers the documentation format, types of breaking changes, versioning strategy, and recommended upgrade approaches.

## Purpose and Scope

Breaking changes are modifications to n8n that require users to update their workflows, environment configurations, or other aspects of their setup when upgrading to a newer version. This document explains the technical aspects of how these changes are managed and communicated, helping developers and users understand when and how they need to adapt their n8n implementations.

## Breaking Changes Documentation Process

n8n maintains a comprehensive record of breaking changes to help users navigate version upgrades.

### Documentation Format

Breaking changes are documented in a standardized format in the `BREAKING-CHANGES.md` file, which is part of the n8n codebase. Each breaking change entry contains:

```
# [Version Number]

### What changed?
[Description of the change]

### When is action necessary?
[Conditions under which users need to take action]

### How to upgrade:
[Instructions for adapting to the change - included for more complex changes]
```

This structured approach ensures that users can quickly assess the impact of a change and understand what actions they need to take.

## Types of Breaking Changes

n8n's breaking changes can be categorized into several types, each affecting different parts of the system:

### Environment Variable Changes

Changes to environment variables, including:

* Removal of variables
* Renaming variables
* Modified default values
* Changed behavior of existing variables

### API and System Behavior Changes

Changes to underlying system behavior:

* Worker server binding changes (IPv6 to IPv4)
* Health check endpoint behavior modifications
* Authentication cookie security settings
* File access restrictions
* Metrics prefix changes

### Workflow Execution Changes

Modifications to how workflows execute:

* Execution mode changes/removals
* Expression evaluation changes
* Data handling changes

### Node Functionality Changes

Changes to specific nodes' behavior or properties:

* Renamed nodes
* Modified data structures
* Parameter changes
* Authentication changes

### Database and Infrastructure Changes

Breaking changes related to the database and infrastructure:

* Database schema changes
* Removal of database support
* Binary data handling changes
* Cache behavior modifications

### Dependencies and Requirements

Changes to required dependencies:

* Node.js version requirements
* Package manager changes
* Crypto algorithm changes

## Versioning Strategy

n8n follows semantic versioning (SemVer), where:

* Major versions (1.0.0) may contain breaking changes
* Minor versions (0.1.0) add functionality in a backward-compatible manner
* Patch versions (0.0.1) contain backward-compatible bug fixes

## Recommended Upgrade Approach

When upgrading n8n with breaking changes, follow these recommended steps:

1. **Review the breaking changes documentation** before upgrading to understand what changes might affect your instance.
2. **Backup your system** - For significant updates (especially database-related changes), export your workflows and credentials.
3. **Test the upgrade** in a non-production environment first.
4. **Apply necessary changes** to your workflows, environment variables, or configuration based on the breaking changes documentation.
5. **Upgrade n8n** to the new version.
6. **Verify functionality** after the upgrade to ensure everything works as expected.
7. If needed, **import workflows and credentials** that were previously exported.

## Conclusion

n8n's breaking changes management follows a structured approach to minimize disruption while allowing the platform to evolve. By documenting changes thoroughly and providing clear upgrade paths, users can navigate version transitions with confidence.

When upgrading your n8n installation, always review the breaking changes documentation for the versions you're moving through, especially if you're upgrading across multiple versions at once.
